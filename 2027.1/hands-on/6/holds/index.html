Index

A hold says "these seats are mine for 10 minutes, while I pay". The invariant: a seat belongs to at most one live hold. Everything in this step is about keeping that invariant true when hundreds of fans click the same seats in the same second.

1. Why "check, then update" is not enough

The obvious code reads the seats, checks they are AVAILABLE, then updates them. Under concurrency, two transactions can interleave:

sequenceDiagram
    autonumber
    participant A as Fan A (tx 1)
    participant DB as PostgreSQL
    participant B as Fan B (tx 2)
    A->>DB: SELECT status FROM seats WHERE id IN (7,8)
    DB-->>A: AVAILABLE, AVAILABLE
    B->>DB: SELECT status FROM seats WHERE id IN (7,8)
    DB-->>B: AVAILABLE, AVAILABLE
    A->>DB: UPDATE seats SET status='HELD', hold_id=A ...
    B->>DB: UPDATE seats SET status='HELD', hold_id=B ... (waits for A's row locks)
    A->>DB: COMMIT
    DB-->>B: update proceeds — overwrites A's hold
    B->>DB: COMMIT
    Note over A,B: both fans got a 201 for seats 7 and 8: DOUBLE BOOKING

PostgreSQL's default isolation, READ COMMITTED, does not prevent this lost update: each statement sees committed data, but nothing ties B's decision (made on the SELECT) to the data when B writes. Three fixes:

Strategy How On conflict Good when
Pessimistic SELECT … FOR UPDATE locks the rows until commit; the second transaction waits, then sees HELD 409 after waiting contention is high (the flash sale: everybody wants the same 100 seats)
Optimistic read without locks; UPDATE … WHERE version = :v; 0 rows changed → someone was faster 409 immediately, the transaction rolls back contention is low; no waiting, no lock queues
Conditional update UPDATE … WHERE id IN (…) AND status = 'AVAILABLE' and check the row count 409 immediately a single statement can express the check (a variant of optimistic)
Serializable isolation SET TRANSACTION ISOLATION LEVEL SERIALIZABLE the database aborts one transaction (40001), the app retries complex invariants over many rows

-- Seats of every event, and the holds that reserve them for a few minutes.
-- event_id refers to catalog.events, but there is NO foreign key across services.
CREATE TABLE inventory.seats (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_id     BIGINT        NOT NULL,
    section      VARCHAR(10)   NOT NULL,
    seat_row     INTEGER       NOT NULL,
    seat_number  INTEGER       NOT NULL,
    price        NUMERIC(10,2) NOT NULL,
    status       VARCHAR(10)   NOT NULL DEFAULT 'AVAILABLE'
                 CHECK (status IN ('AVAILABLE', 'HELD', 'SOLD')),
    hold_id      UUID,
    version      INTEGER       NOT NULL DEFAULT 0,          -- optimistic locking
    UNIQUE (event_id, section, seat_row, seat_number)       -- also the index for "seats of an event"
);

CREATE TABLE inventory.holds (
    id          UUID         PRIMARY KEY,
    event_id    BIGINT       NOT NULL,
    user_id     VARCHAR(64)  NOT NULL,
    status      VARCHAR(10)  NOT NULL CHECK (status IN ('ACTIVE', 'CONFIRMED', 'RELEASED', 'EXPIRED')),
    expires_at  TIMESTAMPTZ  NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- which seats each hold asked for: lets us AUDIT double bookings afterwards
CREATE TABLE inventory.hold_seats (
    hold_id  UUID   NOT NULL REFERENCES inventory.holds (id),
    seat_id  BIGINT NOT NULL REFERENCES inventory.seats (id),
    PRIMARY KEY (hold_id, seat_id)
);

-- Event 1 (the flash sale): 30 sections x 40 rows x 50 seats = 60,000 seats.
INSERT INTO inventory.seats (event_id, section, seat_row, seat_number, price)
SELECT 1, 'S' || lpad(s::text, 2, '0'), r, n, 250 + (s % 5) * 100
FROM generate_series(1, 30) AS s, generate_series(1, 40) AS r, generate_series(1, 50) AS n
ORDER BY s, r, n;

-- Events 2..100: 5 sections x 10 rows x 10 seats = 500 seats each.
INSERT INTO inventory.seats (event_id, section, seat_row, seat_number, price)
SELECT e, 'S' || lpad(s::text, 2, '0'), r, n, 80 + s * 20
FROM generate_series(2, 100) AS e, generate_series(1, 5) AS s,
     generate_series(1, 10) AS r, generate_series(1, 10) AS n
ORDER BY e, s, r, n;

package boxoffice.inventory;

import java.time.Duration;
import java.time.OffsetDateTime;
import java.time.ZoneOffset;
import java.util.List;
import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.HttpStatus;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.server.ResponseStatusException;

/**
 * Holds: "these seats are mine for 10 minutes". The one rule that must never break:
 * a seat belongs to at most ONE live hold. Three ways to (try to) enforce it are
 * selectable with INVENTORY_LOCKING, so you can measure each one.
 */
@Service
public class HoldService {

    private static final Logger log = LoggerFactory.getLogger(HoldService.class);

    private record Seat(long id, String status, int version) { }

    private final JdbcClient jdbc;
    private final String locking;
    private final Duration holdTtl;
    private final int maxSeats;

    public HoldService(JdbcClient jdbc,
                       @Value("${inventory.locking}") String locking,
                       @Value("${inventory.hold-ttl}") Duration holdTtl,
                       @Value("${inventory.max-seats-per-hold}") int maxSeats) {
        this.jdbc = jdbc;
        this.locking = locking;
        this.holdTtl = holdTtl;
        this.maxSeats = maxSeats;
        log.info("seat locking strategy: {}", locking);
    }

    @Transactional        // READ COMMITTED (PostgreSQL's default), on the primary
    public HoldOut hold(String userId, HoldIn in) {
        var seatIds = in.seatIds().stream().distinct().sorted().toList();
        if (seatIds.size() > maxSeats) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "at most " + maxSeats + " seats per hold");
        }
        var holdId = UUID.randomUUID();
        var expiresAt = OffsetDateTime.now(ZoneOffset.UTC).plus(holdTtl);

        switch (locking) {
            case "naive" -> holdNaive(in.eventId(), seatIds, holdId);
            case "optimistic" -> holdOptimistic(in.eventId(), seatIds, holdId);
            default -> holdPessimistic(in.eventId(), seatIds, holdId);
        }

        jdbc.sql("""
                INSERT INTO inventory.holds (id, event_id, user_id, status, expires_at)
                VALUES (:id, :eventId, :userId, 'ACTIVE', :expiresAt)""")
                .param("id", holdId).param("eventId", in.eventId())
                .param("userId", userId).param("expiresAt", expiresAt)
                .update();
        for (var seatId : seatIds) {
            jdbc.sql("INSERT INTO inventory.hold_seats (hold_id, seat_id) VALUES (:holdId, :seatId)")
                    .param("holdId", holdId).param("seatId", seatId)
                    .update();
        }
        return new HoldOut(holdId, in.eventId(), "ACTIVE", expiresAt, seatIds);
    }

    // ---- strategy 1: check-then-act, no lock (WRONG on purpose) ---------------
    private void holdNaive(long eventId, List<Long> seatIds, UUID holdId) {
        var seats = read(eventId, seatIds, "");
        requireAvailable(seats, seatIds);
        // race window: another transaction may have read the same AVAILABLE seats and
        // be about to run this same UPDATE — both will "win"
        jdbc.sql("UPDATE inventory.seats SET status = 'HELD', hold_id = :holdId WHERE id IN (:ids)")
                .param("holdId", holdId).param("ids", seatIds)
                .update();
    }

    // ---- strategy 2: pessimistic, SELECT ... FOR UPDATE -----------------------
    private void holdPessimistic(long eventId, List<Long> seatIds, UUID holdId) {
        // row locks until commit; a second transaction on the same seats WAITS here.
        // Locking in id order (ORDER BY id) prevents deadlocks between overlapping holds.
        var seats = read(eventId, seatIds, "ORDER BY id FOR UPDATE");
        requireAvailable(seats, seatIds);
        jdbc.sql("UPDATE inventory.seats SET status = 'HELD', hold_id = :holdId, version = version + 1 WHERE id IN (:ids)")
                .param("holdId", holdId).param("ids", seatIds)
                .update();
    }

    // ---- strategy 3: optimistic, compare-and-set on a version column ---------------
    private void holdOptimistic(long eventId, List<Long> seatIds, UUID holdId) {
        var seats = read(eventId, seatIds, "");                      // no lock
        requireAvailable(seats, seatIds);
        for (var seat : seats) {
            int changed = jdbc.sql("""
                    UPDATE inventory.seats
                    SET status = 'HELD', hold_id = :holdId, version = version + 1
                    WHERE id = :id AND version = :version AND status = 'AVAILABLE'""")
                    .param("holdId", holdId).param("id", seat.id()).param("version", seat.version())
                    .update();
            if (changed == 0) {
                // someone changed this seat after we read it: give up (the exception rolls back)
                throw new ResponseStatusException(HttpStatus.CONFLICT, "seat " + seat.id() + " was just taken");
            }
        }
    }

    private List<Seat> read(long eventId, List<Long> seatIds, String suffix) {
        return jdbc.sql("SELECT id, status, version FROM inventory.seats "
                        + "WHERE event_id = :eventId AND id IN (:ids) " + suffix)
                .param("eventId", eventId).param("ids", seatIds)
                .query((rs, n) -> new Seat(rs.getLong("id"), rs.getString("status"), rs.getInt("version")))
                .list();
    }

    private static void requireAvailable(List<Seat> seats, List<Long> seatIds) {
        if (seats.size() != seatIds.size()) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "some seats do not belong to this event");
        }
        if (seats.stream().anyMatch(s -> !"AVAILABLE".equals(s.status()))) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "some seats are not available");
        }
    }

    // ---- reading, confirming and releasing a hold (always on the primary) -----

    @Transactional        // NOT readOnly: read-your-writes, the user just created it
    public HoldOut find(String userId, UUID holdId) {
        var hold = jdbc.sql("""
                SELECT id, event_id, status, expires_at FROM inventory.holds
                WHERE id = :id AND user_id = :userId""")
                .param("id", holdId).param("userId", userId)
                .query((rs, n) -> new HoldOut(rs.getObject("id", UUID.class), rs.getLong("event_id"),
                        rs.getString("status"), rs.getObject("expires_at", OffsetDateTime.class), List.of()))
                .optional()
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "hold not found"));
        var seatIds = jdbc.sql("SELECT seat_id FROM inventory.hold_seats WHERE hold_id = :id ORDER BY seat_id")
                .param("id", holdId).query(Long.class).list();
        return new HoldOut(hold.id(), hold.eventId(), hold.status(), hold.expiresAt(), seatIds);
    }

    /** Payment succeeded (lab 7 calls this): seats become SOLD. */
    @Transactional
    public HoldOut confirm(String userId, UUID holdId) {
        int changed = jdbc.sql("""
                UPDATE inventory.holds SET status = 'CONFIRMED'
                WHERE id = :id AND user_id = :userId AND status = 'ACTIVE' AND expires_at > now()""")
                .param("id", holdId).param("userId", userId)
                .update();
        if (changed == 0) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "hold is not active (expired, released or unknown)");
        }
        jdbc.sql("UPDATE inventory.seats SET status = 'SOLD', version = version + 1 WHERE hold_id = :id")
                .param("id", holdId).update();
        return find(userId, holdId);
    }

    @Transactional
    public void release(String userId, UUID holdId) {
        int changed = jdbc.sql("""
                UPDATE inventory.holds SET status = 'RELEASED'
                WHERE id = :id AND user_id = :userId AND status = 'ACTIVE'""")
                .param("id", holdId).param("userId", userId)
                .update();
        if (changed == 0) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "no active hold " + holdId);
        }
        freeSeatsOf(holdId);
    }

    private void freeSeatsOf(UUID holdId) {
        jdbc.sql("""
                UPDATE inventory.seats SET status = 'AVAILABLE', hold_id = NULL, version = version + 1
                WHERE hold_id = :id AND status = 'HELD'""")
                .param("id", holdId).update();
    }

    /**
     * Every 5 s, expire old holds and free their seats. FOR UPDATE SKIP LOCKED lets several
     * inventory replicas run this job at the same time without processing the same hold twice.
     */
    @Scheduled(fixedDelay = 5000)
    @Transactional
    public void expireHolds() {
        int freed = jdbc.sql("""
                WITH expired AS (
                    UPDATE inventory.holds SET status = 'EXPIRED'
                    WHERE id IN (SELECT id FROM inventory.holds
                                 WHERE status = 'ACTIVE' AND expires_at < now()
                                 ORDER BY expires_at
                                 LIMIT 500
                                 FOR UPDATE SKIP LOCKED)
                    RETURNING id)
                UPDATE inventory.seats
                SET status = 'AVAILABLE', hold_id = NULL, version = version + 1
                WHERE status = 'HELD' AND hold_id IN (SELECT id FROM expired)""")
                .update();
        if (freed > 0) {
            log.info("expired holds freed {} seats", freed);
        }
    }
}

Read it strategy by strategy:

  • naive: read(…, "") then an unconditional UPDATE. The comment marks the race window.
  • pessimistic: read(…, "ORDER BY id FOR UPDATE"). The second transaction blocks on the row locks; when the first commits, PostgreSQL re-reads the locked rows, the second sees HELD, and requireAvailable throws 409. Locking in a fixed order (ORDER BY id) matters: fan A holding seats 7→8 and fan B holding 8→7 in opposite order would deadlock.
  • optimistic: no locks; the UPDATE only succeeds if version is still the one we read. If another transaction changed the seat in between, 0 rows change, we throw, and @Transactional rolls back everything (including seats already updated in the loop).
  • Every hold also checks that all seats belong to the event (400 otherwise) and limits a hold to 6 seats.
  • find, confirm and release filter by user_id: a fan cannot see or cancel somebody else's hold (that would be an IDOR, insecure direct object reference — OWASP API #1).
  • expireHolds runs every 5 s on every replica; FOR UPDATE SKIP LOCKED lets several replicas share the work without blocking each other or processing a hold twice — the same trick used by job queues built on PostgreSQL.

import java.util.List;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/** Read-only queries: they run on the REPLICA (readOnly = true), so they may be slightly stale. */
@Service
public class SeatQueries {

    private final JdbcClient jdbc;

    public SeatQueries(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional(readOnly = true)
    public List<SectionAvailability> availability(long eventId) {
        return jdbc.sql("""
                SELECT section,
                       count(*) FILTER (WHERE status = 'AVAILABLE') AS available,
                       count(*) FILTER (WHERE status = 'HELD')      AS held,
                       count(*) FILTER (WHERE status = 'SOLD')      AS sold
                FROM inventory.seats
                WHERE event_id = :eventId
                GROUP BY section
                ORDER BY section""")
                .param("eventId", eventId)
                .query((rs, n) -> new SectionAvailability(rs.getString("section"),
                        rs.getLong("available"), rs.getLong("held"), rs.getLong("sold")))
                .list();
    }

    @Transactional(readOnly = true)
    public List<SeatOut> seats(long eventId, String section) {
        return jdbc.sql("""
                SELECT id, section, seat_row, seat_number, price, status
                FROM inventory.seats
                WHERE event_id = :eventId AND section = :section
                ORDER BY seat_row, seat_number""")
                .param("eventId", eventId)
                .param("section", section)
                .query((rs, n) -> new SeatOut(rs.getLong("id"), rs.getString("section"),
                        rs.getInt("seat_row"), rs.getInt("seat_number"),
                        rs.getBigDecimal("price"), rs.getString("status")))
                .list();
    }

    /** Seats that belong to more than one live hold: must always be 0. Reads the PRIMARY. */
    @Transactional
    public long doubleBookedSeats() {
        return jdbc.sql("""
                SELECT count(*) FROM (
                    SELECT hs.seat_id
                    FROM inventory.hold_seats hs
                    JOIN inventory.holds h ON h.id = hs.hold_id
                    WHERE h.status IN ('ACTIVE', 'CONFIRMED')
                    GROUP BY hs.seat_id
                    HAVING count(*) > 1) AS doubles""")
                .query(Long.class)
                .single();
    }
}

import java.util.List;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.reactive.EnableWebFluxSecurity;
import org.springframework.security.config.web.server.ServerHttpSecurity;
import org.springframework.security.oauth2.core.DelegatingOAuth2TokenValidator;
import org.springframework.security.oauth2.jwt.JwtClaimValidator;
import org.springframework.security.oauth2.jwt.JwtValidators;
import org.springframework.security.oauth2.jwt.NimbusReactiveJwtDecoder;
import org.springframework.security.oauth2.jwt.ReactiveJwtDecoder;
import org.springframework.security.web.server.SecurityWebFilterChain;

@Configuration
@EnableWebFluxSecurity
public class SecurityConfig {

    /** Which routes are open, which need a valid token, which need the admin scope. */
    @Bean
    SecurityWebFilterChain security(ServerHttpSecurity http) {
        return http
                .csrf(ServerHttpSecurity.CsrfSpec::disable)        // stateless API, no cookies
                .authorizeExchange(ex -> ex
                        // open: getting a token, and the public keys to check one
                        .pathMatchers("/auth/register", "/auth/login", "/auth/.well-known/**").permitAll()
                        // open: browsing the catalog
                        .pathMatchers(HttpMethod.GET, "/catalog/**").permitAll()
                        // admin only: changing the catalog (scope claim "user admin")
                        .pathMatchers("/catalog/**").hasAuthority("SCOPE_admin")
                        // open: seat maps and availability (lab 6); holds need a token
                        .pathMatchers(HttpMethod.GET, "/inventory/events/**").permitAll()
                        // health, metrics, routes: the edge never forwards /actuator from outside
                        .pathMatchers("/actuator/**").permitAll()
                        // everything else (and every future route): any valid token
                        .anyExchange().authenticated())
                .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
                .build();
    }

    /** Signature from the JWKS of auth, plus expiry, issuer and audience checks. */
    @Bean
    ReactiveJwtDecoder jwtDecoder(@Value("${spring.security.oauth2.resourceserver.jwt.jwk-set-uri}") String jwksUri,
                                  @Value("${jwt.issuer}") String issuer,
                                  @Value("${jwt.audience}") String audience) {
        var decoder = NimbusReactiveJwtDecoder.withJwkSetUri(jwksUri).build();
        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
                JwtValidators.createDefaultWithIssuer(issuer),     // exp, nbf, iss
                new JwtClaimValidator<List<String>>("aud", aud -> aud != null && aud.contains(audience))));
        return decoder;
    }
}

// Lab 6: the 10:00 flash sale. 200 fans fight for the first 100 seats of section S01
// of event 1. Each fan tries to hold 2 seats; some change their mind and release.
// Run it once per locking strategy (INVENTORY_LOCKING) and compare.
//   bash scripts/reset-inventory.sh && k6 run load/flash-sale.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter } from 'k6/metrics';
import { BASE_URL, loginFans, authHeaders } from './lib.js';

// a 409 (seat taken) is an expected answer in a flash sale, not a failure
http.setResponseCallback(http.expectedStatuses(200, 201, 204, 409));

const held = new Counter('holds_created');
const conflicts = new Counter('holds_conflict');

export const options = {
  scenarios: {
    fans: { executor: 'constant-vus', vus: Number(__ENV.VUS || 200), duration: __ENV.DURATION || '30s' },
  },
  summaryTrendStats: ['avg', 'med', 'p(95)', 'p(99)', 'max'],
  thresholds: {
    'http_req_duration{name:hold}': ['p(95)<1000'],
    http_req_failed: ['rate<0.01'],
    holds_created: ['count>0'],
    holds_conflict: ['count>=0'],
  },
};

export function setup() {
  const tokens = loginFans(50);
  const seats = http.get(`${BASE_URL}/inventory/events/1/seats?section=S01`).json();
  return { tokens, seatIds: seats.slice(0, 100).map((s) => s.id) };   // rows 1-2: the best seats
}

export default function (data) {
  const token = data.tokens[__VU % data.tokens.length];
  const i = Math.floor(Math.random() * (data.seatIds.length - 1));
  const body = JSON.stringify({ eventId: 1, seatIds: [data.seatIds[i], data.seatIds[i + 1]] });

  const res = http.post(`${BASE_URL}/inventory/holds`, body, { ...authHeaders(token), tags: { name: 'hold' } });
  check(res, { 'hold answered 201 or 409': (r) => r.status === 201 || r.status === 409 });
  if (res.status === 201) {
    held.add(1);
    sleep(0.5);
    if (Math.random() < 0.7) {                       // 70% give up: the seats go back on sale
      http.del(`${BASE_URL}/inventory/holds/${res.json('id')}`, null, { ...authHeaders(token), tags: { name: 'release' } });
    }
  } else if (res.status === 409) {
    conflicts.add(1);
    sleep(0.2);
  }
}

}

These numbers come from one run on a busy laptop — yours will differ — but the shape is what matters: naive created more holds than the seats allow and the audit found 9 double-booked seats; pessimistic and optimistic always end with 0. With only 100 seats, most attempts are 409 (the seats are gone), which the script counts as an expected answer, not an error. Compare also the latency of the hold requests: pessimistic transactions queue on row locks, optimistic ones fail fast — here optimistic had the lowest p99, because a conflicting fan learns "taken" without waiting for anybody's lock.

Think first: if pessimistic locking is correct, why would anyone use optimistic locking?

Locks cost waiting. When contention is low (fans spread over 60,000 seats, most holds touch different rows), optimistic locking never waits and almost never conflicts, so it is cheaper. When contention is high (everybody wants the first rows), optimistic locking turns into a storm of conflicts and retries, while pessimistic locking serializes the requests neatly. Measure your contention before choosing — and remember that the real flash-sale design also reduces contention before the database: a waiting room (lab 7) admits fans at a rate the inventory can absorb.

In the interview

For "design Ticketmaster", say explicitly: "seat inventory is the one place that needs strong consistency; I will use a relational database with row-level locking (or conditional updates) for holds, with a TTL on each hold, and everything else — catalog, search, seat maps — can be eventually consistent and cached." Then mention the hot-row problem: thousands of fans on the same 100 seats serialize on their locks, so queue them before the database.
