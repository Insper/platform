Tools

The tools of the trade, grouped by job. For each one: what it is in one line, when to reach for it, the lab where we use it in this course, and its official site. The course stack is deliberately small: Docker Compose to run everything locally, k6 to load-test, OpenTelemetry + grafana/otel-lgtm to observe, Toxiproxy to inject faults, kind or minikube for Kubernetes, GitHub Actions and Argo CD to deliver, and LiteLLM + Ollama + pgvector for the AI service. The alternatives are listed so you recognize them in job descriptions and engineering blogs.

About the links

Links go to each project's official site or official repository. Tools change fast: check the current documentation before copying a command from a blog post, and pin versions in your docker-compose.yaml and CI files.

Load testing

k6 Load-testing tool scripted in JavaScript, with thresholds that fail a run (great for CI) You want readable scripts, smoke/load/stress/spike/soak profiles and pass/fail thresholds Hands-on 2, every "Measure it" step, CI gate in Hands-on 11 k6.io
Gatling Load-testing tool with scenarios in Java, Kotlin or Scala and detailed HTML reports Your team lives on the JVM and wants code-first scenarios Alternative to k6 gatling.io
Locust Load testing with user behavior written in Python You prefer Python, or need custom protocols Alternative to k6 locust.io

wrk2 Tiny HTTP benchmarking tool with a constant request rate, corrected for coordinated omission You need a quick, honest latency distribution at a fixed rate Class 15 (coordinated omission) github.com/giltene/wrk2
vegeta HTTP load tool with a constant attack rate, usable as a CLI or Go library Open-model (fixed-rate) tests from the command line Alternative for quick tests github.com/tsenart/vegeta
oha / hey Minimal command-line HTTP load generators A ten-second sanity check, not a test campaign Quick checks oha · hey

Open vs closed workload

Most tools default to a closed model (N virtual users, each waiting for its response before sending the next). Real internet traffic is closer to an open model (requests arrive at a rate, whether or not the server keeps up). k6's constant-arrival-rate and ramping-arrival-rate executors, wrk2 and vegeta generate open load; use them when you want to see queues build up. See Class 15 · Load testing.

Learn the job, not just the tool

Interviewers rarely care whether you used k6 or Gatling. They care whether you know what to measure (percentiles at a target rate, the knee, the bottleneck) and why. Learn one tool per job well, and be able to say what its alternatives do differently.
