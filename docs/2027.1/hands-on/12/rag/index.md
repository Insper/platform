# 2. RAG with pgvector

A language model knows nothing about *this week's* BoxOffice catalog, and when it does not know, it
makes things up with confidence. **Retrieval-augmented generation** (RAG) fixes the first problem and
reduces the second: before the model answers, the service *retrieves* the documents most related to
the question and puts them in the prompt, with instructions to answer only from them and to cite them.
The theory is in the [RAG and memory class](../../../classes/ai-systems/rag-memory/index.md).

``` diagram-sim
flowchart LR
    subgraph ingest [ingest: once, and when the catalog changes]
        cat[catalog API] --> txt[event -> text]
        txt --> emb1[embedding model]
        emb1 --> pg[("assistant.documents (vector 768)")]
    end
    subgraph query [every question]
        q[question] --> emb2[embedding model]
        emb2 -->|"ORDER BY embedding <=> q LIMIT k"| pg
        pg --> ctx[top-k documents]
        ctx --> llm[LLM: answer + citations]
    end
```

## Embeddings in one paragraph

An **embedding model** maps a text to a vector (here, 768 numbers) so that texts with similar meaning
get vectors pointing in similar directions. "Is there a festival in Recife?" and "Festival #74 at Arena
Recife…" end up close, even with few words in common. **Cosine distance** (`<=>` in pgvector) measures
the angle between two vectors: 0 for the same direction, up to 2 for opposite ones; `1 - distance` is
the similarity the search returns.

- `vector(768)` is pgvector's column type; the dimension must match the embedding model.
- **HNSW** (Hierarchical Navigable Small World) is an *approximate* nearest-neighbour index: a layered
  graph that finds the closest vectors in logarithmic time instead of comparing the query with every
  row. It trades a little recall for a lot of speed; `vector_cosine_ops` builds it for the cosine
  distance the queries use.
- The schema is created by the service at startup (`CREATE … IF NOT EXISTS`), not by Flyway: the
  assistant is the only Python service and keeps its single table simple. Each service still owns its
  own schema, as in lab 0.

| Decision | Why |
|---|---|
| one document per event, written as a sentence | the embedding model was trained on sentences, not JSON; "what, where, when, how much" is what fans ask |
| `search_document:` / `search_query:` prefixes | `nomic-embed-text` was trained with them; without them, retrieval quality drops |
| batches of 32 texts per embedding call | fewer round trips; the model processes a batch faster than 32 single calls |
| `ON CONFLICT … DO UPDATE` | re-running the ingestion updates changed events instead of duplicating them |
| `ORDER BY embedding <=> %s LIMIT k` | exactly the shape the HNSW index accelerates (an `ORDER BY` on the distance, with a `LIMIT`) |

The catalog seed of lab 1 has 200 000 events; embedding all of them on a laptop CPU would take hours.
The lab ingests the first `limit` events (300 here); production systems embed incrementally, as
events are created or changed (an outbox event of lab 7 is the natural trigger).

A test run with `nomic-embed-text`:

``` text
| question | relevant | first relevant rank |
|---|---|---|
| When is Play #7? | 1 | 1 |
| When is Festival #42? | 1 | 1 |
| When is Festival #118? | 1 | 1 |
| When is Play #199? | 1 | 1 |
| When is Concert #256? | 1 | 1 |
| Is there any festival in Recife? | 9 | 1 |
| Is there any play in Curitiba? | 6 | 1 |
| Is there any match in Salvador? | 9 | 1 |
| Is there any concert in Manaus? | 6 | 1 |
| Is there any festival in São Paulo? | 10 | 1 |
| the big festival night at the stadium in São Paulo | 1 | 3 |

hit@5 = 1.00   MRR = 0.94   (11 questions)
```

**hit@k** is the share of questions with at least one right document in the top k; **MRR** (mean
reciprocal rank) also rewards putting it first (rank 1 → 1, rank 3 → ⅓). The last question is the hard
one: "the big festival night" is event 1, *BoxOffice Fest — Stadium Night*, and the generic festivals at
the same stadium rank above it. Dates and exact names are where pure vector search is weakest; real
systems combine it with keyword search (**hybrid search**) and a **reranker**.

??? question "Why evaluate retrieval separately from the answers?"

    If the right document is not in the context, no model can answer correctly — and the failure looks
    like a "bad model". Measuring retrieval alone tells you which half of the pipeline to fix, and it is
    cheap: no LLM call, fully deterministic.
