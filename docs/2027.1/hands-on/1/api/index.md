The first step designs the **contract** of `catalog`: which resources it exposes, which requests it accepts and what it answers. In an interview this is step 3 of the framework (*API and data model*); in a real team it is what other teams code against, so it deserves care before any SQL exists.

## 2. Design the resources

Two **resources**, each a noun with a collection URL and an item URL, all under the service prefix `/catalog` (see the [conventions of lab 0](../../0/index.md#boxoffice-services-and-ports)):

``` mermaid
classDiagram
    class Venue {
        Long id
        String name
        String city
        int capacity
    }
    class Event {
        Long id
        String title
        Category category
        OffsetDateTime startsAt
        BigDecimal priceFrom
    }
    class Category {
        <<enumeration>>
        CONCERT
        SPORTS
        FESTIVAL
        THEATER
    }
    Event "*" --> "1" Venue : takes place at
    Event --> Category
```

| Decision | Choice | Why |
|---|---|---|
| Identifiers | `BIGINT` generated by the database | simple, compact, easy to pick at random in k6 (`1..200000`) |
| Collections | **paginated** (`page`, `size` ≤ 50) | an unbounded `GET /events` on 200,000 rows would be a self-inflicted outage |
| Default listing | **upcoming** events, soonest first | it is what the home page shows; past events are not for sale |
| Money | `BigDecimal` / `NUMERIC(10,2)` | never `double` for prices |
| Time | `OffsetDateTime` / `TIMESTAMPTZ`, ISO-8601 in JSON | events happen in different time zones |
| Errors | RFC 9457 `application/problem+json` | one machine-readable error shape for every service |
| Create | `201 Created` + `Location: /catalog/events/{id}` | the client learns where the new resource lives |

## 4. Controllers

Controllers only translate HTTP into method calls: they validate the input, call the service and choose the status code. No SQL, no business rule.

``` { .java title="services/catalog/src/main/java/boxoffice/catalog/VenueController.java" .copy linenums="1" }
--8<-- "docs/2027.1/hands-on/1/code/services/catalog/src/main/java/boxoffice/catalog/VenueController.java"
```

How validation works here:

- `@Valid @RequestBody EventIn in` checks the annotations of the record (`@NotBlank`, `@NotNull`, `@PositiveOrZero`) and answers **400** before the method runs.
- `@Min(0)` / `@Max(50)` on `page` and `size` use Spring's built-in **method validation** (Spring Framework 6.1+): `?size=5000` is rejected with **400** instead of loading 5,000 rows.
- With `spring.mvc.problemdetails.enabled: true` (next step), both cases come back as `application/problem+json`.

!!! example "What a client sees"

    ``` { .http }
    GET /catalog/events?size=500 HTTP/1.1

    HTTP/1.1 400 Bad Request
    Content-Type: application/problem+json

    {"detail":"Validation failure","instance":"/catalog/events",
     "status":400,"title":"Bad Request"}
    ```

!!! tip "In the interview"

    When you sketch the API, say three things out loud: the **resources and verbs** (`GET /events?city=&page=`), the **pagination strategy** (offset now; *keyset* — `WHERE starts_at > :last` — when users scroll deep, because `OFFSET 100000` still reads 100,000 rows) and the **error model**. Interviewers listen for whether you bound every collection.

!!! warning "Pitfalls"

    - **Returning the entity**: a lazy `venue` serialized outside a transaction throws `LazyInitializationException`, or worse, a new column leaks to clients (a password hash, a cost price).
    - **Unbounded lists**: every collection endpoint needs a maximum page size.
    - **`200` for everything**: status codes are part of the contract; proxies, caches and k6 checks rely on them.

The controllers depend on `CatalogService`, which you write in the next step together with the entities and the database: [2. Persistence](../persistence/index.md).
