!!! abstract "In this lab"

    - Build **`catalog`**, the first BoxOffice service: a REST API for events and venues with Spring Boot 4, PostgreSQL, Flyway and an OpenAPI document.
    - Package it as a **container image** and run it with its database using **Docker Compose**.
    - **Measure it** with a k6 smoke test: the latency of each endpoint when the service is *not* under load.

Every ticketing site starts with the same page: *what is on, where, and when?* In BoxOffice that is the job of `catalog`. It is the most **read-heavy** service of the system — during a flash sale, millions of fans refresh the event page while only a handful of administrators ever change it — and that is why it will be the guinea pig for load balancing (lab 3), caching (lab 5) and indexing (lab 6). Today you build the simplest version that works, the **monolith-first** step of the scaling journey.

## What you will build

``` diagram-sim
sequenceDiagram
    autonumber
    actor Fan
    participant C as catalog :8082<br/>(Spring Boot)
    participant DB as db :5432<br/>(PostgreSQL, schema catalog)
    Fan->>C: GET /catalog/events?city=Recife
    C->>DB: SELECT events JOIN venues WHERE city = ? ORDER BY starts_at LIMIT 20
    DB-->>C: 20 rows
    C->>DB: SELECT count(*) ... (total for the page links)
    DB-->>C: 20001
    C-->>Fan: 200 {items: [...], page: 0, totalItems: 20001}
```

The service follows a classic three-layer structure — **controller** (HTTP, validation, DTOs) → **service** (business rules, transactions) → **repository** (SQL through JPA) — with one rule that matters for everything that follows: the API never exposes the database entities, only **records** (`EventOut`, `VenueOut`) that you control.

| Method | Path | Body | Answer |
|---|---|---|---|
| `GET` | `/catalog/events?city=&page=&size=` | — | `200` page of upcoming events, soonest first |
| `GET` | `/catalog/events/{id}` | — | `200` event with its venue, or `404` |
| `POST` | `/catalog/events` | `EventIn` | `201` + `Location` header, or `400` |
| `PUT` | `/catalog/events/{id}` | `EventIn` | `200`, `400` or `404` |
| `DELETE` | `/catalog/events/{id}` | — | `204` or `404` |
| `GET` | `/catalog/venues` · `/catalog/venues/{id}` | — | `200` venues |
| `POST` | `/catalog/venues` | `VenueIn` | `201` |
| `GET` | `/actuator/health` · `/catalog/openapi` · `/swagger-ui.html` | — | health, OpenAPI document, interactive docs |

The database starts with **50 venues in 10 cities and 200,000 events** (one per hour from March 2027), generated by a Flyway migration[^1]. Event **1** is the course's flash-sale show: *BoxOffice Fest — Stadium Night*, at a 60,000-seat stadium. A realistic volume of data is deliberate: a query that is instant on 10 rows can take tens of milliseconds on 200,000, and that is exactly what you will measure.

??? question "Think first: run the smoke test twice. Why is the second run faster?"

    The first requests after a start hit a **cold** JVM (classes loading, the JIT still interpreting bytecode), an empty connection pool and PostgreSQL pages not yet in its buffer cache. After a few hundred requests everything is **warm**. Load tests therefore always have a warm-up, and you should never compare a cold run with a warm one.

!!! note "If your numbers differ"

    Absolute values depend on your CPU, on the memory given to Docker and on what else is running (close the browser tabs and IDEs you do not need). What must hold everywhere: every check passes, the detail is several times faster than the listing, and the second run is faster than the first. If the detail p95 is above ~100 ms with one user, Docker is probably short of CPU or memory (`docker stats`).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `Bind for 0.0.0.0:5432 failed: port is already allocated` | a local PostgreSQL is running | stop it (`brew services stop postgresql`, `sudo systemctl stop postgresql`) or map `"15432:5432"` in `docker-compose.yaml` |
| build fails in `mvn … package` with `Could not resolve dependencies` | no internet, proxy, or a broken download | check the connection and run `docker compose build --no-cache catalog` |
| `catalog` stays `starting`/`unhealthy` | it is still migrating/starting (the first start seeds 200,000 events), or it crashed | `docker compose logs catalog`; look for `Started CatalogApplication` or the first `ERROR` |
| `Connection to localhost:5432 refused` in the catalog logs | `DB_HOST` is not `db` inside Compose | use the `docker-compose.yaml` of this page unchanged |
| `Validate failed: Migrations have failed validation` | an applied migration was edited | restore the file; on your laptop only, `docker compose down -v` resets the database |
| `curl: (7) Failed to connect to localhost port 8082` | the container is not up yet, or port not published | `docker compose ps`; wait for `healthy` |
| `?city=São Paulo` returns 400 or nothing | the space and the `ã` must be URL-encoded | use `?city=S%C3%A3o%20Paulo` (k6 does it with `encodeURIComponent`) |
| `exec format error` on Apple Silicon | an image built for another architecture | all images used here are multi-arch; remove any `platform:` line and rebuild |

!!! success "Best practices in this lab"

    - **Configure through environment variables with safe defaults** — `DB_POOL_SIZE: ${DB_POOL_SIZE:-10}` in `docker-compose.yaml` and `application.yaml` lets lab 2 change the pool without a rebuild; the formula behind the number is in [Queueing](../../classes/estimation/queueing/index.md).
    - **Fix the resources of every container** — `cpus: "1.0"` and `memory: 768M` make one replica's capacity a measurable number ([Numbers — servers](../../classes/estimation/numbers/index.md)).
    - **Version the schema as migrations** — Flyway's `V1__create_catalog.sql` and `V2__seed_catalog.sql` rebuild the same database on every machine; a schema changed by hand drifts.
    - **Expose a readiness endpoint and let the platform use it** — the Compose `healthcheck` calls `/actuator/health/readiness`; load balancers rely on the same signal ([Load balancing — health checks](../../classes/edge/load-balancing/index.md#health-checks)).
    - **Write the latency requirement as a test threshold** — `load/smoke.js` fails when a p95 passes its limit ([Requirements](../../classes/intro/requirements/index.md)).
