This step connects the API to PostgreSQL: **entities** map the tables, **repositories** hold the queries, the **service** defines the transactions and **Flyway** creates and seeds the schema. Each service owns one schema — `catalog` here — and nothing else touches it.

``` diagram-sim
flowchart LR
    ctl["EventController<br/>VenueController"] --> svc["CatalogService<br/>@Transactional"]
    svc --> repo["EventRepository<br/>VenueRepository"]
    repo --> jpa["Hibernate (JPA)"]
    jpa --> pool["HikariCP<br/>10 connections"]
    pool --> db[("PostgreSQL<br/>schema catalog")]
    fly["Flyway<br/>V1, V2"] -->|at startup| db
```

Keep the **connection pool** in mind: every request that touches the database borrows one of its 10 connections for the duration of its transaction. In lab 2 that number turns out to be the ceiling of the whole service.

|---|---|

| `@Enumerated(EnumType.STRING)` | stores `CONCERT`, not `0`: reordering the enum cannot corrupt data |
| `@ManyToOne(fetch = LAZY)` | the venue is loaded only when needed — or eagerly with `join fetch` in a query |

!!! warning "The N+1 query problem"

    Without `join fetch`, listing 20 events runs **1** query for the events and then **20** more, one per venue, when `EventOut.of` touches `event.getVenue()`. With `join fetch e.venue`, it is a single SQL `JOIN`. N+1 is invisible with one user and devastating under load: 21 round trips instead of 1, each one holding a pooled connection.

A `Page<Event>` result costs **two** queries: the page itself (`... ORDER BY starts_at LIMIT 20 OFFSET ?`) and a `count(*)` over every matching row, so the client can show "page 1 of 1,001". On 200,000 events without an index, both are full scans — the listing you will measure in lab 2, cache in lab 5 and index in lab 6.

## 3. The service layer

`CatalogService` is where transactions begin and end. Read methods use `@Transactional(readOnly = true)`: Hibernate skips dirty checking, and in lab 6 the same flag routes reads to a replica.

``` { .java title="services/catalog/src/main/java/boxoffice/catalog/CatalogService.java" .copy linenums="1" }
--8<-- "docs/2027.1/hands-on/1/code/services/catalog/src/main/java/boxoffice/catalog/CatalogService.java"
```

Business rules that live here:

- an unknown event or venue id → `404 Not Found`;
- creating or updating an event with a venue that does not exist → `400 Bad Request`;
- `updateEvent` does not call `save`: the entity is *managed* inside the transaction and Hibernate writes the `UPDATE` at commit (*dirty checking*).

## 4. Migrations with Flyway

The schema is code: versioned SQL files in `src/main/resources/db/migration`, applied **in order, once**, at startup. Flyway records what it ran in `catalog.flyway_schema_history`, so every environment — your laptop, CI, Kubernetes — converges to the same schema.

Rules of the game:

- Name: `V<version>__<description>.sql` (two underscores). Versions only grow.
- **Never edit a migration that already ran** somewhere: Flyway checks a checksum and refuses to start. To change the schema, add `V3__...`.
- `ddl-auto: validate` makes Hibernate *check* that the entities match the tables, but never change them: one owner for the schema.
- The seed uses `generate_series`: 200,000 rows in about a second, identical on every machine — so everybody's measurements are comparable.

| Property | Why |
|---|---|
| `${DB_HOST:localhost}` … | the connection comes from the environment variables of [lab 0](../../0/index.md#boxoffice-services-and-ports); the defaults work from your IDE |
| `hikari.maximum-pool-size: ${DB_POOL_SIZE:10}` | the pool size, configurable without rebuilding — you will change it in lab 2 |
| `flyway.schemas: catalog` | Flyway creates the schema and keeps its history table there |
| `open-in-view: false` | no lazy loading during JSON serialization: the transaction ends in the service |
| `tomcat.mbeanregistry.enabled` | publishes `tomcat.threads.busy`, used in lab 2 |
| `health.probes.enabled` | `/actuator/health/liveness` and `/readiness`, used by Compose now and Kubernetes in lab 10 |

??? question "Think first: why does the `count(*)` query matter for performance?"

    It reads **every** matching row (20,000 per city) just to produce one number, on every page request. Options: cache it (lab 5), estimate it, drop it and return only "has next page" (Spring's `Slice`), or make it cheap with an index (lab 6). Many large sites show "1,000+ results" for exactly this reason.

!!! tip "In the interview"

    Name the **access patterns** before the tables: "the home page lists upcoming events by city, sorted by date, 20 at a time; the event page reads one event by id". The schema and, later, the indexes follow from those queries — not the other way around.

## 6. Checkpoint: does it compile?

If you have JDK 21 and Maven installed (lab 0), compile the service now, before Docker enters the picture:

``` { .bash .copy }
cd services/catalog
mvn -B -DskipTests package
cd ../..
```

You should see, at the end:

``` { .text }
[INFO] Building catalog 1.0.0
[INFO] BUILD SUCCESS
[INFO] Total time:  4.142 s
```

and a `services/catalog/target/app.jar` of about 60 MB (the application plus all its libraries). A `COMPILATION ERROR` names the file and line: compare that file with the full listing above. The service cannot *run* yet — it needs PostgreSQL, which the next step provides.
