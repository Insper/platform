Este passo conecta a API ao PostgreSQL: **entidades** mapeiam as tabelas, **repositórios** guardam as consultas, o **serviço** define as transações e o **Flyway** cria e popula o schema. Cada serviço é dono de um schema — aqui, `catalog` — e nada mais mexe nele.

``` diagram-sim
flowchart LR
    ctl["EventController<br/>VenueController"] --> svc["CatalogService<br/>@Transactional"]
    svc --> repo["EventRepository<br/>VenueRepository"]
    repo --> jpa["Hibernate (JPA)"]
    jpa --> pool["HikariCP<br/>10 conexões"]
    pool --> db[("PostgreSQL<br/>schema catalog")]
    fly["Flyway<br/>V1, V2"] -->|na inicialização| db
```

Guarde o **pool de conexões** na cabeça: toda requisição que toca o banco pega emprestada uma das suas 10 conexões durante a sua transação. No lab 2 esse número vira o teto do serviço inteiro.

| Anotação | Significado |
|---|---|
| `@Table(name = "events", schema = "catalog")` | schema explícito: a tabela pertence a este serviço |
| `@GeneratedValue(strategy = IDENTITY)` | o banco gera o id (`GENERATED BY DEFAULT AS IDENTITY`) |
| `@Enumerated(EnumType.STRING)` | grava `CONCERT`, não `0`: reordenar o enum não corrompe dados |
| `@ManyToOne(fetch = LAZY)` | o local só é carregado quando preciso — ou de imediato com `join fetch` em uma consulta |

!!! warning "O problema das N+1 consultas"

    Sem `join fetch`, listar 20 eventos executa **1** consulta para os eventos e mais **20**, uma por local, quando `EventOut.of` toca `event.getVenue()`. Com `join fetch e.venue`, é um único `JOIN` em SQL. O N+1 é invisível com um usuário e devastador sob carga: 21 idas e voltas em vez de 1, cada uma segurando uma conexão do pool.

Um resultado `Page<Event>` custa **duas** consultas: a página em si (`... ORDER BY starts_at LIMIT 20 OFFSET ?`) e um `count(*)` sobre todas as linhas que casam, para o cliente mostrar "página 1 de 1.001". Em 200.000 eventos sem índice, as duas são varreduras completas — a listagem que você vai medir no lab 2, colocar em cache no lab 5 e indexar no lab 6.

Regras de negócio que vivem aqui:

- um id de evento ou local desconhecido → `404 Not Found`;
- criar ou atualizar um evento com um local que não existe → `400 Bad Request`;
- `updateEvent` não chama `save`: a entidade está *gerenciada* dentro da transação e o Hibernate escreve o `UPDATE` no commit (*dirty checking*).

Regras do jogo:

- Nome: `V<versão>__<descrição>.sql` (dois sublinhados). As versões só crescem.
- **Nunca edite uma migration que já rodou** em algum lugar: o Flyway confere um checksum e se recusa a iniciar. Para mudar o schema, acrescente `V3__...`.
- `ddl-auto: validate` faz o Hibernate *verificar* que as entidades batem com as tabelas, mas nunca alterá-las: um único dono para o schema.
- A carga inicial usa `generate_series`: 200.000 linhas em cerca de um segundo, idênticas em toda máquina — então as medições de todos são comparáveis.

| Propriedade | Por quê |
|---|---|
| `${DB_HOST:localhost}` … | a conexão vem das variáveis de ambiente do [lab 0](../../0/index.md#boxoffice-services-and-ports); os padrões funcionam a partir da sua IDE |
| `hikari.maximum-pool-size: ${DB_POOL_SIZE:10}` | o tamanho do pool, configurável sem recompilar — você vai mudá-lo no lab 2 |
| `flyway.schemas: catalog` | o Flyway cria o schema e mantém nele a sua tabela de histórico |
| `open-in-view: false` | nada de lazy loading durante a serialização do JSON: a transação termina no serviço |
| `tomcat.mbeanregistry.enabled` | publica `tomcat.threads.busy`, usado no lab 2 |
| `health.probes.enabled` | `/actuator/health/liveness` e `/readiness`, usados pelo Compose agora e pelo Kubernetes no lab 10 |

??? question "Pense antes: por que a consulta `count(*)` importa para o desempenho?"

    Ela lê **todas** as linhas que casam (20.000 por cidade) só para produzir um número, a cada requisição de página. Opções: colocá-la em cache (lab 5), estimá-la, descartá-la e devolver só "tem próxima página" (o `Slice` do Spring), ou torná-la barata com um índice (lab 6). Muitos sites grandes mostram "1.000+ resultados" exatamente por isso.

!!! tip "Na entrevista"

    Nomeie os **padrões de acesso** antes das tabelas: "a página inicial lista os próximos eventos por cidade, ordenados por data, 20 por vez; a página do evento lê um evento pelo id". O schema e, depois, os índices decorrem dessas consultas — não o contrário.

## 6. Ponto de controle: compila? { #6-checkpoint-does-it-compile }

Se você tem o JDK 21 e o Maven instalados (lab 0), compile o serviço agora, antes de o Docker entrar em cena:

``` { .bash .copy }
cd services/catalog
mvn -B -DskipTests package
cd ../..
```

Você deve ver, no fim:

``` { .text }
[INFO] Building catalog 1.0.0
[INFO] BUILD SUCCESS
[INFO] Total time:  4.142 s
```

e um `services/catalog/target/app.jar` de cerca de 60 MB (a aplicação mais todas as suas bibliotecas). Um `COMPILATION ERROR` aponta o arquivo e a linha: compare esse arquivo com a listagem completa acima. O serviço ainda não *roda* — precisa do PostgreSQL, que o próximo passo fornece.
