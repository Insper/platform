\ansclass{3}{Distributed Systems}
\ans{1} (a) $1 - 0.999^N$: \final{0.3\% with 3 machines, 63\% with 1\,000, 95\% with 3\,000}. (b) $e^{-0.001 \times 1\,000} = e^{-1} \approx 0.37$, so $\approx$ 63\%. (c) At scale \final{some machine is broken almost every day}: failure is the normal case, so the design needs replicas, automatic failover, timeouts and idempotent retries, not hope.
\careful{adding the probabilities ($3\,000 \times 0.1\% = 300\%$). The complement $1 - (1-p)^N$ never exceeds 100\%.}
\ans{2} (a) \final{I}: \texttt{GET}, \texttt{PUT /holds/A-12} (sets a state), \texttt{DELETE} (a second call may return 404 but the state is the same), the \final{conditional \texttt{UPDATE}} (the second run finds \texttt{HELD} and changes nothing). \final{N}: \texttt{POST /orders} (each call creates an order) and \texttt{sold = sold + 1} (each call adds one). (b) The request was lost; \texttt{payment} crashed before charging; the charge happened and \final{the reply was lost}; \texttt{payment} is \final{still working (slow)}. In the last two a plain retry charges twice. The caller cannot tell which case it is in.
\careful{treating a timeout as a failure. A timeout means \emph{unknown}: the operation may have happened.}
\ans{3} (a) \texttt{INSERT INTO idempotency\_keys(key, request\_hash) \dots{} ON CONFLICT DO NOTHING} (0 rows $\to$ duplicate: return the stored response); \texttt{INSERT INTO orders \dots{} (981, \dots)}; \texttt{UPDATE idempotency\_keys SET response = '\{"orderId": 981\}'}, then commit. (b) Atomicity: \final{the key exists if and only if the order exists}. Stored elsewhere after the commit, a crash between the two leaves an order without a key, and the retry creates a second one. (c) The retry hits the unique key, the stored response is read and the fan gets \final{201, order 981, no duplicate}. (d) Every retry looks new: \final{the key must identify the logical operation} (one tap on ``Pay''), not the attempt. (e) So that \texttt{payment}'s own retries to the provider cannot charge twice; after 24 h the provider forgets the key, so \final{retries must stop well within 24 h} (then reconcile).
\careful{deduplicating in memory on one replica: the retry lands on another replica, or after a restart, and the duplicate goes through.}
\ans{4} (a) \final{$\approx 3 \times 10^{-7}$ (never), 22\% and 69\%}: on the on-sale, more than two out of three fans see an empty ``My tickets''. (b) \final{Read-your-writes}: read from the leader for a short window (1--5 s) after the fan's own write, or send the write's position (the PostgreSQL WAL LSN) as a version token and read from a replica that has reached it. (c) \final{Monotonic reads}: each read hit a replica with a different lag. Pin the fan's session to one replica (or keep a version token). (d) Seats and holds: \final{linearizable}; payments: linearizable and idempotent; ``My tickets'': \final{read-your-writes}; seat counter: monotonic reads; catalog: \final{eventual}; interest counters: eventual (a CRDT counter).
\careful{``fixing'' it by sending every read to the leader: the replicas existed because the leader could not take all the reads.}
\ans{5} (a) Majority / tolerated: 3: 2/1; 4: \final{3/1}; 5: 3/2; 7: 4/3. \final{Four nodes tolerate no more than three} and need a bigger majority: more cost, same safety. (b) 2$+$2$+$1 losing a 2-node zone keeps 3 of 5: \final{writes continue}. 3$+$1$+$1 losing the 3-node zone keeps 2: \final{writes stop}. No zone may hold a majority. (c) $0.970299 + 0.029403 =$ \final{99.97\%}, better than one node (99\%). (d) $R + W > 3$: \final{(2, 2), (3, 1) and (1, 3)}; (1, 1) and (2, 1) may read stale data. Pick \final{(2, 2)}: tolerates one node down for both reads and writes; (3, 1) blocks writes and (1, 3) blocks reads with one node down. (e) The storage \final{rejects A's write: $33 < 34$}, the highest token it has seen. Without the token, A would overwrite B believing it still holds the lock.
\careful{believing that a lock with a timeout is enough. A paused process cannot see that its lease expired; only the storage can stop it.}
\ans{6} (a) Release stamped .090, hold .060: \final{the release wins}, A-12 shows FREE and Carla, already charged, has no seat. (b) $20 \times 10^{-6} \times 86\,400 \approx$ \final{1.7 s per day}; $40 \times 10^{-6} \times 600 =$ \final{24 ms} in 10 minutes. (c) Consumer: $\max(0, 2) + 1 =$ \final{3}; \texttt{TicketIssued} carries \final{4}; \texttt{notification}: $\max(1, 4) + 1 =$ \final{5}. (d) \final{Neither}: no vector is $\le$ the other element-wise, so the events are concurrent, a real conflict. (e) \final{A single authority} for each seat (one primary decides with a conditional update), a version column checked on write (compare-and-set), a per-key log (a Kafka partition keyed by seat), or a database with hybrid clocks.
\careful{reading $L(a) < L(b)$ as ``$a$ happened before $b$''. A Lamport clock only guarantees the other direction.}
\ans{7} (a) Seats and payments: \final{CP}, the minority side refuses (``cannot confirm right now, try again'', 503) rather than sell A-12 twice. Catalog and likes: \final{AP}, both regions answer, possibly stale, and merge later. (b) $5 \times (1\text{--}2) =$ \final{5--10 ms} in a region; $5 \times 200 =$ \final{1 s} across the Atlantic. PACELC: keep each seat's writes in its \final{home region} (synchronous standby in another zone) instead of replicating synchronously across continents. (c) T1 create order PENDING (C1: cancel); T2 seat HELD $\to$ reserved for payment (C2: release, FREE); T3 \final{charge the card with an idempotency key: the pivot}; T4 seat SOLD, order CONFIRMED, ticket (retried until it succeeds, no compensation). Declined at T3: \final{C2 then C1}, in reverse order. (d) 2PC \final{blocks} while the coordinator is down (seats stay locked), needs every participant up (availability $a^{n+1}$), costs two round trips with fsyncs, and the payment provider does not take part in your 2PC.
\careful{calling the design ``CA''. Partitions happen; the only choice is what each piece of data does when they do.}
