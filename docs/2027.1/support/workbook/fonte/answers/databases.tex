\ansclass{6}{Databases \& Data Systems}
\ans{1} Seats and holds: \final{SQL Database} (an invariant across rows; 60\,000 rows is tiny, the hard part is write contention). Orders: $20 \times 10^6 \times 1$ KB $=$ \final{20 GB/year, SQL}. Posters and PDFs: \final{Object Store} (+ CDN), the database keeps only the key. Clickstream: $10^8 \times 200$ B $=$ \final{20 GB/day, Data Warehouse}. Sessions and counters: \final{Cache} (or a key-value NoSQL DB) with TTL. Vectors: $10^5 \times 1\,024 \times 4$ B $\approx$ \final{400 MB, Vector DB} (pgvector next to the data is enough at this size).
\careful{choosing NoSQL ``for scale'' for the seats. The seats need a transaction across rows, and their volume is small.}
\ans{2} (a) $8\,192/16 = 512$, \final{$\approx 500$}: $500^2 = 250$ thousand, $500^3 = 125$ million, \final{$500^4 = 62.5$ billion} keys. (b) 3 million seats: \final{3 levels}; a billion rows: \final{4 levels}. The root and the next level are always in memory, so a lookup reads 1--2 pages from disk. (c) B-tree: $1 + 8\,192/100 \approx$ \final{83$\times$}; LSM: $2 + 3 \times 5 =$ \final{17$\times$}. Gate scans are write-heavy and append-only: an \final{LSM engine} (a wide-column store keyed by \texttt{(event\_id, gate)}).
\careful{measuring write cost in rows. Storage engines write pages (B-tree) or rewrite files during compaction (LSM).}
\ans{3} (a) Both \texttt{SELECT}s read AVAILABLE; Alice's \texttt{UPDATE} commits; Bob's \texttt{UPDATE}, which waited for the row lock, then overwrites it. Both are told they hold A-12: a \final{lost update (check-then-act race)}; read committed does not prevent it. (b) \texttt{UPDATE seats SET status='HELD', held\_by=:me, hold\_expires\_at=now()+10 min WHERE event\_id=42 AND seat\_id='A-12' AND status='AVAILABLE'}: \final{the winner is the transaction whose UPDATE changed 1 row}; the loser sees 0 rows and answers 409. Last line of defence: a \final{unique constraint on \texttt{tickets(event\_id, seat\_id)}}. (c) \final{8 tickets}: each tab checked a snapshot in which the other's seats did not exist (\final{write skew}). Repeatable read (snapshot isolation) does \final{not} stop it. Fixes: \final{serializable} isolation (abort with 40001, retry) or \final{lock one limit row} (\texttt{customer\_event\_limits \dots\ FOR UPDATE}) before checking.
\careful{raising the isolation level ``a bit'' and believing it is fixed: repeatable read still allows write skew.}
\ans{4} (a) $1/0.005 =$ \final{200 holds/s}, whatever the machine; 2 M fans would need $\approx 10\,000$ s ($\approx$ 3 hours). (b) 40 rows: $40/0.005 =$ \final{8\,000/s}; 60\,000 rows: $1.2 \times 10^7$ by the formula, so \final{10\,000/s, the database limit}. (c) The lock lasts 500 ms: \final{2 holds/s}. Never keep a transaction (and its locks) open across a network call; hold with an expiry, commit, and pay afterwards.
\careful{believing a bigger database fixes a hot row. The limit is $1/t$ per row, not CPU.}
\ans{5} (a) $e^{-300/20} \approx$ \final{0\%}; $e^{-1.5} \approx$ \final{22\%}; $e^{-0.3} \approx$ \final{74\%}: during the on-sale three in four fans would see an empty list. (b) Read from the \final{primary for owned data} or for some seconds after a write (BoxOffice: 30 s after a purchase); or \final{wait until the replica has replayed the write's position} (LSN). (A sticky replica gives only monotonic reads.) (c) $2\,000 \times 0.005 =$ \final{10 busy connections}; a pool of 20--30 absorbs bursts. $20 \times 50 =$ \final{1\,000 connections}: put a pooler (\final{PgBouncer}, transaction pooling) in between. (d) $R + W > 3$: (1,3), (2,2), (2,3), (3,1), (3,2), (3,3). Only \final{$W = 2$, $R = 2$} tolerates one node down for both.
\careful{using replicas for decisions or for the user's own just-written data: replicas are for reads that can be a little stale.}
\ans{6} (a) 0x1F $\to$ \final{B}; 0x9A $\to$ \final{C}; 0xF3 wraps around $\to$ \final{A}. (b) \final{Only the keys between 0x40 and 0x80, from C to D}; A and B are untouched. (c) \texttt{h mod 9 = h mod 10} for 1 key in 10, so \final{90\% move} with mod $N$; with consistent hashing \final{$\approx 1/10$}. (d) All the stadium's seats live on one partition: \final{one hot shard} while the others idle. Use \final{\texttt{(event\_id, section)}} ($\approx$ 40 sections), plus sharded counters for ``seats left'' and the waiting room.
\careful{adding partitions to fix a hot key: the key still maps to one partition. Change the key, cache it or queue the writers.}
\ans{7} (a) $10^9 \times 1$ KB $=$ \final{1 TB}, 5\,000 writes/s: now partitioning is justified. Key \final{\texttt{customer\_id}}: high cardinality, even spread and the hot query (``my orders'') hits one partition. \texttt{created\_at} sends all new writes to the last range; \texttt{event\_id} makes the stadium show one hot shard. (b) $20$ GB $\times 730 \approx$ \final{15 TB raw}; 3 of 30 columns: \final{$\approx$ 1.5 TB}; with compression \final{$\approx$ 150--300 GB} (and less with date pruning). (c) A good drawing has: SQL as the system of record (orders partitioned, seats by section, a synchronous standby); a cache for the catalog; an outbox or CDC (change data capture) feeding Kafka, from which the search index and the warehouse are updated (\final{no dual writes}); posters in the object store behind the CDN with pre-signed uploads; vectors in pgvector or a Vector DB; reports never on the production database.
\careful{sharding first: a 50 GB database needs indexes, a cache and replicas, not partitions.}
