Roteiro: (1) o que torna um serviço nuvem; (2) a pilha de responsabilidade; (3) subindo a pilha, um modelo de cada vez; (4) blocos gerenciados; (5) comparando os modelos; (6) como escolher, a loja componente por componente; (7) erros comuns.

Cada opção traça uma linha diferente entre o que seu time opera e o que outra pessoa opera. É essa linha que um modelo de serviço em nuvem define.

Controle e portabilidade caem conforme o tempo até entrar no ar melhora. O FaaS é o ponto fora da curva na portabilidade: o código é escrito contra a API de um fornecedor.

A loja poderia usar um único provedor (na AWS: EKS para os serviços, RDS para o Postgres) ou misturar provedores (GitHub para o código e o CI): o que decide é o requisito de cada componente, como mostra o próximo slide. O Cloud Run functions se chamava Cloud Functions.

Setas: cliente → gateway → account e order; account e order → Postgres; order → Redis e Kafka; o Kafka aciona o Lambda, que envia o e-mail pelo SES.
